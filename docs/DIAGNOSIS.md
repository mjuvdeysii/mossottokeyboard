# 诊断：为什么真机上还是不如普通输入法「灵活」（2026-11-03）

> 问题（产品负责人，真机测试）：比之前好很多，但仍不如普通输入法灵活；怀疑是常用句子库、词库的问题。
> 本文只记录**实测**与**推断**，两者分开写。所有数字都在本机 `-O`、带句子模型（`sentence.gram`）、
> 305 句调参集上取得。

## 一、事实：24 个错例是什么形状

`PERFECT_DEBUG=1 ... bench` 列出全部失败句。24 句里：

| 类别 | 例 | 条数 |
|---|---|---|
| 的 / 得 | 标题写的太长了、最近睡的不太好 | 2 |
| 他 / 她 | 他会自己穿鞋了、她最喜欢小兔子、他是我的大学同学 | 3 |
| 其它同音词 | 收货/收获、离/里、再/在、傻子/沙子、经/已经、超/潮、有/又、纸/值、哥哥/各个、还/换 | 19 |

**全部 24 条都是「同一个拼音、不同字」**——没有一条是"打不出来"，也没有一条是缺词。

## 二、事实：这些词在词库里吗

| 词 | 在库里的位置（全拼，`type`） |
|---|---|
| 收获 / 收货 | 21.58 / **23.16**（收货第 2） |
| 各个 / 哥哥 | 21.28 / **21.46**（相差 0.18） |
| 傻子 | 首选（句子读成「玩了傻子」，是上下文没把它压下去） |

**结论（事实）：词都在库里，而且大多就在前二。问题不在覆盖率，在同音排序。**

## 三、事实：三个"加宽"实验都没用

| 实验 | 结果（305 句首选命中） |
|---|---|
| `beam` 4（默认） | 281 |
| `beam` 16 / 40 | 283 / 283（+2 句，+0.7%，延迟 6 倍） |
| 语言模型权重 GW 0.5 / 1.0 / 1.5 / 2.5 | 279 / **281** / 278 / 273 |
| 上下文长度 3 / 4 / 5 字 | 281 / 282 / 282（+1 句） |

推断：**搜索宽度、模型权重、上下文长度都已在该引擎的极值附近**，继续加宽是负收益。

## 四、推断：普通输入法赢在哪

1. **个人学习**：他/她、的/得这类，主流输入法靠用户纠正几次就固定；
   Mosto 现在学的是"词"，对「在某个词后面选过哪个同音字」这类上下文偏好覆盖不足。
2. **口语短语统计**：「玩沙子」「收货地址」这种，靠的是大规模聊天语料里的搭配概率；
   万象模型偏书面（48 GB 现代中文语料），口语搭配可能被书面搭配压住。
3. **规则兜底**：的/得、他/她 有确定性规则（得 后面接补语、她 指女性），主流输入法会硬编码一部分；
   Mosto 完全交给语言模型，于是两边都"差一点点"。

## 五、下一步（待会议定，按影响排序）

1. **上下文偏好的学习**：用户在同一前文里改选过某个同音字，下次在该前文后把它提前（不是整词加分）。
   验收：`learn.same` 不降；构造 20 条「同前文同音字」用例，命中率从 0 提到 ≥60%。
2. **的/得 与 他/她 的规则层**：只在前文能判定时生效（动词后 + 补语 → 得；女性称谓 → 她）。
   验收：24 个错例里这两类 5 条修好 ≥4；`sentences.perfect` 不降。
3. **口语搭配的证据**：先把「玩沙子」「收货地址」这类在语料里的实际搭配概率量出来，
   再判断是补一张小搭配表，还是调模型权重——**没有测量之前不补词表**。

## 六、不做的事

- 不加宽 beam、不抬模型权重、不改上下文长度——三项都已实测为负收益或零收益。
- 不靠"补一批词"解决同音排序问题。

## 七、第 1 项落地记录（2026-11-03）

**上下文偏好学习已进 `Engine/`**：

- `UserDictionary` 新增 `learnPreference(context:text:)` / `preference(context:text:)`，存在 userdict 旁边的
  `context-prefs.json`，与词库分开（只影响排序，不改词库）。
- `Decoder.link` 里按「前三个字 + 当前词」查偏好，命中加 `preferenceBoost × strength`（一次 0.5，两次以上 1）。
- 键盘在**用户没有选首选**时记录：`KeyboardViewController` 提交处（`i > 0`）把「光标前文本 + 已提交的部分」
  与该词一起写入。`EngineHost` 负责异步落盘。

**实测（`PREF` 钩子，仅用于测量）**

| 喂入偏好 | 305 句首选命中 | 说明 |
|---|---|---|
| 无 | 281 | 当时构建（未含 的/得 规则） |
| `园玩了\|沙子` + `\|她` | **283** | 该构建上 +2；**质检组 R8 更正**：在含 的/得 的当前构建上同一条偏好是 281→283、叠加 的/得 后为 **285**，283 不能当作当前构建的绝对值 |

**未验证的部分（写清楚）**：真机上"用户改一次以后就稳定"的收敛速度没有测；跨重启的持久化只做了文件写入，
没有做端到端验证；`context-prefs.json` 损坏时的行为未测（词库那份有 corrupt 兜底，这份没有）。

**已知代价**：`mixed.sentences.top1` 72.50（80 句、`-O`、带句模、CI run #141 与本地一致），相对关掉漏按的 73.75 低 1.25 分——**质检组 R8 更正**：73.75 这个对照值出自 R5 的消融（`rounds/R5.md`），不在 R6；且 72.50 与门槛 72.5 恰好相等，**余量 0 句**，已记入 R8 待办。

## 八、第 2 项落地：的 / 得 规则层（2026-11-03）

- 规则：首选里「的」后面紧跟补语的开头（太、不、很、非常、特别、真、挺、好、快、慢、更、最、多、少）时，
  若**同一键数**下存在把那个「的」写成「得」的读法，就把它提到第一。只换顺序，不改文本、不重排其余候选。
- 实测（305 句调参集，`-O`，带句子模型）：

  | 指标 | 改前 | 改后 |
  |---|---|---|
  | 错句数 | 24 | **22** |
  | `sentences.perfect` | 92.13 | **92.79** |
  | `sentences.true` | 89.18 | **89.84** |
  | 其它门禁 | — | 全 PASS（`gate.coverage` 32/32，九宫格与混输不变） |

- 修好的两条：`标题写得太长了`、`最近睡得不太好`。
- 一次失败尝试记录在案：先写成了「给含『的+补语』的候选扣分再整体重排」，结果 24 → **26**（把单字的候选排到了前面）。
  改为「只把对应的『得』读法提到第一」才成立——规则层只该动那一个位置，不该重排整个候选表。
