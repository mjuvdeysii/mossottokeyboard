# R1 · 打磨会议纪要与本轮方案

- 依据：构建 219 的 CI 截图（`snap_std`，日光 / 夜光）、测试门禁数字、引擎实测错例（`/tmp/claude-0/engine`，构建 219 的 `lexicon.bin` 与 `sentence.gram`）、代码。
- 主持：独立代理（未参与实现）。
- 排序标准：对一位正在连续打字的用户的影响。输入准确率与稳定性排第一。

## 结论

1. **本轮主攻长句里按错一个键的情况。** 键位全对时，长句已经基本打对（全拼 92.1%）。但长句中间多按或漏按一个键时，首选常常多出或换掉一个字：全拼漏按 48.5%、多按 81.0%，小鹤多按 57.7%。本次现场取证 25 例，首选只对 10 例。
2. **配套三件事：**
   - 纠错说明要完整，「打错了什么→改成了什么」在长句里不能消失。
   - CI 截图要如实：Mosto 目前在键盘截图里一次都没出现。
   - 图标和 Mosto 的蝙蝠翅膀要认得出。
3. **App 侧：** 「了解」页的演示卡片加一条通往「上手」页、可以亲手试的路径，同时修正文案里的否定句和过度承诺。
4. **验收：** 门禁同一套测试，目标见「本轮方案」各项。留出集 sentences3 / sentences4 只报告、不调参。新增的「R1 现场错例」从 10/25 提到至少 15/25。截图逐张做日夜对照。

## 各组发言

### 一 · 应用设计

**1. 纠错说明的小字对比度不到 4.5:1。**
- 证据：在 `day_letters_composing.png` 首选「你好」下方，「hap」这一段取文字最深的像素与浅紫底色比较，对比度约 4.1:1。`night_letters_composing.png` 约 4.3:1，`day_plain_composing.png` 约 3.7:1。字号是 10.5 pt（`CandidateViews.swift` 的 `fixFont`），颜色是 `Theme.secondaryText`。
- 影响：这行小字是纠错可见的唯一载体。用户扫一眼看不清，就无法判断要不要撤回。
- 改法：`CandidateRow.caption(for:)` 中，「打的键」一段改用正文墨色的 70% 或更深，在三种底色（Mosto 日光、Mosto 夜灯、简洁）上都要达到 ≥ 4.5:1。「改成」一段保留强调色并同样达标。「原键」标签一并检查。

**2. 简洁风格的夜光截图里出现了 Mosto 的金色余光，与真机不一致。**
- 证据：`night_plain_numbers.png` 左上角有一团金色光晕。真机代码在 `KeyboardViewController.swift:486` 已经写了 `tintView.isHidden = Theme.plain`，但 `SnapshotRenderer.swift:94–98` 构造 `AmbientLightView` 时没有按风格隐藏。
- 影响：设计组按截图审查时会误判简洁风格「混进了 IP 元素」。
- 改法：截图器与键盘共用同一条判断，见方案第 3 项。

**3. 九宫格截图的纠错说明是假数据。**
- 证据：`day_t9_composing.png` 首选下方写着「hap→hao」。九宫格的按键是成组的，`Decoder.fixes(for:)` 遇到成组按键直接返回空（`Decoder.swift:1003`）。真机上九宫格不会出现这行字。截图里的说明来自 `SnapshotRenderer.swift:112–113` 的固定候选。
- 影响：截图把一项不存在的能力展示成了已有能力。
- 改法：九宫格截图改用不带 fixes 的候选。

**4. 图标的翅膀读成了两片叶子或兔耳，翼尖贴着画布边缘。**
- 证据：`AppIcon-1024.png` 与 `AppIcon-Dark-1024.png` 中，左翼尖约在 x≈40，右翼尖约在 x≈1000（画布宽 1024），已进入 iOS 图标圆角蒙版的裁切区。翅膀是光滑的桨形，看不到 `docs/MOSTO.md` 写明的「波浪边」，也看不到角色圣经的「背后一对**小**蝙蝠翅膀」。
- 影响：主屏 60 pt 下，翼尖被切掉、轮廓变成两根竖条，品牌识别点丢失。这也违反 STANDARDS 的「蝙蝠翅膀可见」。
- 改法：见方案第 4 项。

### 二 · 内容展示

**1. 纠错说明会在长句里消失，正好是最需要它的时候。**
- 证据：`CandidateRow.caption(for:)` 在 fixes 为空时只写「已纠错」，超过 2 处时只写「纠正 N 处」。引擎实测：
  - `qingbanwokanyixiazhegeppt` 的首选「请把我看一下这个PPT」带纠错标记，`fixes(for:)` 返回为空。
  - `woyongiphonedazii` 的首选「我用iPhone打字」同样如此（CLI 输出 `[corrected ]`）。
  - `mafannibangwoquerenyixiafahuoshjian`（时间漏 i）整句读对了，但走的是简拼通路，没有标出纠错。
- 影响：用户看到浅色底，却不知道改了哪里。这违反产品负责人「纠错要呈现打错了什么→改成了什么」的要求。
- 改法：见方案第 2 项。

**2. README 对长句纠错的描述超过了门禁数字。**
- 证据：README「自动纠错」一行写的是「长句中间多按一个键、漏按一个键……仍能整句读对」。门禁的实际数字是：全拼多按 81.0%、漏按 48.5%，小鹤多按 57.7%，小鹤漏按未测。
- 影响：TestFlight 用户按这句话去试，大约一半会失望，可信度受损。这违反「数字要真实、可复核」。
- 改法：README 与 `TESTFLIGHT.md` 改成带数字和测法的肯定句，例如「长句中间多按一个键：全拼 81% 整句读对；漏按一个键：49%（门禁同一套 305 句，各打一次）」。本轮改进后按新数字更新。

**3. App 文案里有否定堆叠。**
- 证据：
  - `HomeShowcase.swift:465`（`day_app_home3.png` 小鹤双拼一行）：「不切换也完全没关系」。
  - `HomeShowcase.swift` 的 `HomeFooter`：「没有用到 AI 或任何大模型、云端服务」。
  - `XiaoheGuideView.swift:89`：「没有必要为此切换」。
- 影响：读起来像免责声明，不像产品说明。
- 改法：改成肯定句，保留原意和学习成本说明（固定约束）：
  - 小鹤一行：「两种方案在这个键盘上功能相同，全拼用户继续用全拼就好；想换之前先看学习成本。」
  - 页脚：「候选全部来自装在 App 里的开源词库与统计数据，在手机上算出来，全程离线。」
  - 小鹤说明：「全拼速度已经够用，就继续用全拼。」

**4. 「了解」页演示卡的标题与画面不一致。**
- 证据：`day_app_home2.png` 第二张卡的标题是「长句多按、漏按一个键」，画面只演示了漏按（tia→tian），说明也只写了「中间少按了 n」。
- 影响：标题承诺两件事，画面只兑现一件。
- 改法：说明改为「中间少按了 n，整句照样读对；多按一个键也一样」，保留现有画面。

### 三 · 应用交互

**1. 长句首选错了以后，后面几个候选只换最后一个字，正确的句子不在眼前。**

**2. 「了解」页的演示只能看，不能做，像文档。**

**3. 句末多按、按偏一个键，会多出一个字。连续打字时最常见的就是这一下。**

**三类失败：**

  - 代码：`quanpinSpans` 里多按的分支写明「never as the syllable's first key」（`Decoder.swift:316–320`），所以句末单独一键只能当新音节。
  - 说明：小鹤句末单键在输入过程中本来就是「半个字」，#14 #15 不作为本轮目标，只记录。
- **B 错键拼出另一个合法音节，单字词胜出**（#1 #2 #4 #6 #9 #10 #11）：纠错后的读法在语言模型里输给「带 / 一 / 买 / 把」这类高频单字。
  - 相关参数：`midAbbreviationPenalty` 目前是 **0.0**（`Decoder.swift:100`）。#5「开心那」就是 x 被当作句中简拼。
  - 相关参数：`missingPenalty` 9.0，`skipPenalty` 9.0。
- **C 小鹤漏按没有测量**：门禁漏按一项对小鹤直接跳过（`EngineCLI/main.swift` 中 `decoder.scheme == .xiaohe ? [] : sentItems`）。#12 #13 显示小鹤漏一键会整句崩掉。
- 影响：日常聊天和工作消息都是 15–40 键的长句，一句里按偏一下的概率很高。上面的错误都是「按空格前首选错」，用户必须回删。
- 改法：见方案第 1 项。

**2. CI 的「最慢一次解码 522 ms」把冷启动和稳态混在了一起，首键延迟没有被单独测量。**
- 证据：`SnapshotRenderer.swift:250–265` 在 `host.load(...)` 后立刻 `decodeNow`。第一次调用要等引擎装载、模型页换入（`EngineHost.swift:64` 注释估计约 0.2 s），之后才是 400 次随机字母（2–25 键）解码。
- 本机 CLI 实测稳态：全拼 16–37 键长句 8.6–28.2 ms，86 键超长句 38.7 ms，小鹤 2.2–4.0 ms。
- 影响：522 ms 如果是冷启动，就是「键盘刚弹出、第一个字有没有停顿」（TESTFLIGHT 请重点试第 2 条）。字母照常即时写入输入框，候选会晚出现。现在无法区分。
- 改法：FOOTPRINT 拆成三个数：首次解码（冷）、其后 400 次的 p99、最大值，见方案第 3 项。

**3. FOOTPRINT 的内存增量不代表键盘扩展的真实占用。**
- 证据：before 794.4 MB 与 after 795.3 MB 都是整个 App 进程（含截图渲染的图像），+0.9 MB 只说明解码过程没有产生明显的脏内存。内存映射的词库和语言模型是干净页，不计入这个数字；装进扩展、受约 60 MB 上限约束的情况没有被测到。
- 影响：iOS 的扩展内存上限是键盘最常见的闪退原因，现在缺少直接证据。
- 改法：本轮只改测量（在 FOOTPRINT 行补上 400 次解码后的 `phys_footprint` 增量与映射文件常驻页数），不改实现。放在方案第 3 项，不单列。

**4. 安装包因语言模型增大约 400 MB。**
- 证据：`TESTFLIGHT.md` 已知问题。
- 影响：首次下载与更新的门槛。
- 改法：属于准确率与体积的取舍，列入「留待决定」。

## 冲突与取舍

裁决标准：**对一位正在连续打字的用户的影响**。输入准确率与稳定性排第一。

| # | 冲突 | 裁决 | 被否决的意见与理由 |
|---|---|---|---|
| 1 | IP 组提出纠错时让 Mosto 在候选栏眨眼反馈（曝光） vs 设计组的留白、交互组的「打字时候选栏只给候选」 | **否决 IP 组提议** | 打字时 Mosto 本来就让位给候选（`MOSTO.md` §3），这是已经验证过的克制。纠错正发生在用户视线最集中的首选上，旁边一动就会抢走对「hap→hao」的注意。IP 曝光放在空闲、上屏后（已有 `greet()`）和 App 里。 |
| 2 | 开发组提出句末多按「在空格时再改判」 vs 交互组的「所见即所上屏」 | **否决空格时改判** | 首选显示 A、空格上屏 B，会让用户失去对键盘的信任，比偶尔多一个字更伤。句末处理只在解码阶段做，显示什么就上屏什么。 |
| 3 | 提高句中简拼代价（`midAbbreviationPenalty`）修好 B 类 vs 有人故意混打简拼（如 `woxhni`） | **采纳，但设硬约束** | perfect、true、`userword.*` 等门禁不得下降，否则回退这一项。简拼用户是少数，长句按偏是多数；门禁守住多数，参数守住少数。 |
| 4 | 扩大纠错搜索（句末多按、更多漏按分支） vs 延迟 | **采纳，以门禁为界** | `sentences.ms`（全拼 ≤ 16）与 `fuzz.p99.ms`（全拼 ≤ 100、小鹤 ≤ 40）照旧，超出就收窄。准确率排第一，但延迟门禁本来就是稳定性的一部分。 |
| 5 | 交互组曾提出把「了解」页的动画演示换成真键盘 vs 固定约束「改设计不删原有内容」 | **否决替换，改为加「试一试」入口** | 演示动画保留。在卡片上加一条通往「上手」页对应课程的路径，交互化与不删内容两头都满足。 |
| 6 | 内容组要求 README 写出漏按 48.5% 的真实数字 vs 品牌组担心「数字不好看」 | **采纳内容组** | 「数字要真实、可复核」是发布标准。用肯定句写出能做到的比例与测法，本轮改进后数字会上升。 |
| 7 | 设计组认为题图 / 图标键帽上的「A」「中」属于文字，触及「题图不放文字标签」 vs 品牌组认为它们是键盘这个物件本身 | **本轮不改，列入留待决定** | 这两个字是物件上的刻字，不是解释画面的标签，但边界需要产品负责人定。本轮的图标改动只动翅膀与构图，不动键帽。 |
| 8 | 的 / 得、再 / 在、他 / 她 要不要本轮专门调 | **本轮不专门调** | 没有对应的开发集，直接调会过拟合到几句话上。他 / 她在无上下文时本来就不可判，现有「选过一次就记住」是正确方向。本轮把这些句子收进 R1 现场错例作为记录，下一轮再决定是否建专项集。 |

### 1. 长句按错一个键：句末单键、句中简拼、候选去重、小鹤漏按测量

- **负责：** iOS 开发（主）、应用交互
- **改法：**
  - **(a) 句末多按。** `Decoder.swift` 的 `quanpinSpans` 多按分支：输入的**最后一键**允许作为多按（skip）处理，代价用 `skipCost`，与「读作新音节简拼」（`abbreviationPenalty`）由语言模型比较。句中仍保持「不作为音节首键」。小鹤 `xiaoheSpans` 不改句末（半个字是正常的输入中间态）。
  - **(b) 句中简拼。** 对 `midAbbreviationPenalty`（现为 0.0）按 0 / 2 / 4 / 6 扫描，只用 sentences.tsv / sentences2.tsv / mixed.tsv 与门禁的多按、漏按生成句。取 perfect 与 true 不降、missing 最高的一档，写死，不做成设置。
  - **(c) 候选去重。** `decodeLetters` 的 `add(_:_:)` 处：完整句候选与前一候选只差最后一个单字词时，至多保留一个；空出的位置给下一个读法不同的整句（如「打电话」）。
  - **(d) 小鹤漏按测量。** `EngineCLI/main.swift` 的漏按一项对小鹤也跑一遍，本轮只记录基线，不设门槛。
  - **(e) 新增回归集。** `EngineCLI/r1_typos.tsv` 收录上表 25 例（可复现输入），CLI 输出 `r1.top1` 与 `r1.top3`，作为记录指标，不进门禁。sentences3 / sentences4 不参与。

## 总结

构建 219 在「键位全对的长句」上已经很稳。本轮把力气放在连续打字时最常发生的事：长句里按偏、多按、漏按一个键。目标有三个：首选少出错，错了时正确句子留在眼前，改了什么写得出、看得清。

为了让每一轮的 IP 与视觉审查有据可依，先让 CI 截图如实。同时把 Mosto 的蝙蝠翅膀在图标和键盘里做到认得出，并在「了解」页的演示和真实练习之间接上一条路。

所有目标都用门禁同一套测试、截图日夜对照和新增的键盘测试来验收。留出集只用来检验，不用来调参。被否决的提议和需要你拍板的三件事已列在上面。
