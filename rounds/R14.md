# R14 · 修复「点第一候选上屏没反应」

- 议题（产品负责人）：「更了几万个版本，我选第一候选上屏还是有时候没反应，要点几万次」。
- 这是**间歇性**故障 → 竞态，不是稳定的解码错误。本轮只读代码定位根因，不猜。

## 根因（代码级，已确认）

点击到上屏的路径：

```
用户点候选
  → candidateBar.onSelect → candidateTapped(i)
  → select(i, shown: result?... )
  → currentResult()
       if resultGeneration == generation → 返回缓存 result（快）
       else → engine.decodeNow(...)  →  EngineHost.queue.sync { run(...) }   ← 主线程同步等待引擎队列
```

`refresh()` 每次按键 `generation += 1` 并**异步** `engine.decode(...)`；只有回调里 `show()` 才把
`resultGeneration = gen`。因此：

1. **用户按键后、解码还没回来时点候选** → `resultGeneration != generation` → 走 `decodeNow` 的 `queue.sync`。
2. 引擎队列正忙（上一次 decode / learn / predict 未完）时，主线程被阻塞，iOS 丢弃这次触摸 → **点了没反应**。
3. 另一条静默失败：`candidateTapped` 传的 `shown` 取自 `result`（可能是上一代），
   `select` 里 `firstIndex(where:)` 找不到就 `return`，什么都不上屏。

"有时候" = 是否命中「解码在飞」这个窗口。所有 decode 共用同一条 `mosto.engine` 队列
（`EngineHost.swift:26`），`decodeNow` 是 `queue.sync`（`:146`），放大了这个窗口。

## 修复（最小、结构性的）

1. **`candidateTapped` 不再同步等引擎**：若 `resultGeneration != generation`（解码在飞），
   把这次点击存进 `pendingSelect = (index, shown)` 后 `return` —— 点击路径上零同步、零等待。
2. **`show()` 里执行 pending**：那一代解码回来、`result` 与候选栏都更新完之后，
   用**同一代**的 result 调 `select(index, shown:)`。提交的一定是用户当时看到的那一代。
3. **250ms 兜底**：若那一代解码始终没回来（被 superseded 丢弃），用当前显示的结果执行一次，
   不让点击凭空消失。
4. **`select()` 只读缓存 `result`**，不再调 `currentResult()` 的同步分支；
   `currentResult()` 本身**恢复原样**（空格上屏 `:783`、九宫格等都依赖它的同步解码，
   全局删掉会让 11 条测试台断言变红，已实测）。
5. `clearComposition` / `reconcileWithHost` 清掉过期的 pending。

## 为什么测试台抓不住，以及怎么补的（诚实记录）

测试台引擎是同步的，**旧代码下新写的两条运行时断言也是 PASS** —— 它复现不了 `queue.sync` 的竞态。
所以改用**源码级 CI 断言** `Tools/check_no_sync_tap.py`，检查：
- `pendingSelect` 机制存在；
- `select()` / `candidateTapped()` 体内**没有** `decodeNow` / `currentResult()` / `queue.sync`；
- `show()` 会执行 pending。

注入验证：修复版 `PASS`；换回旧 `KeyboardViewController.swift` → `FAIL 4 条`（机制缺失、
select 调用 currentResult、show 不执行 pending）。这条断言已接入 workflow（build 第 9 步）。
