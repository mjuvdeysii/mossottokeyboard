# R7 · 打磨会议纪要与本轮方案

- 议题（产品负责人）：真机反馈「比之前好很多，但仍不如普通输入法灵活」；表情面板与颜文字的两处观感问题；
  以及——**最近的推进变成了「修 bug」，五组开会、每轮一个板块的形式丢了**。这一轮把它接回来。
- 依据：
  - CI：`#143` 全绿（门禁两方案 + 键盘测试台 137 项 + 新的 `engine-slips` 任务），`#145` 在跑。
  - 快照：`ci-logs/snapshots/day_emoji.png`（改前）、改后（9 列 / 78% 字号）。
  - 实测：`docs/DIAGNOSIS.md`（24 条错例全是同音字；beam/权重/上下文三项加宽都无收益）；
    `sentences.perfect 92.13 → 92.79`（的/得 规则层）。
  - 代码：`Keyboard/EmojiPanelView.swift`、`Engine/Decoder.swift`、`Engine/UserDictionary.swift`。
- 主持：独立代理。

## 结论

1. **「不如普通输入法灵活」的原因已经定位并部分解决**：24 条错例全部是同音字排序，不是词库覆盖。
   两条同音规则已落地（上下文偏好学习、的/得），错句 24 → 22，`sentences.perfect` 92.13 → 92.79。
2. **表情面板这一版只算「可用」**：9 列、78% 字号、底栏 36pt 已验证；但**颜文字大小不一**是真的 bug
   （固定 17pt 再自动缩放，长句缩到 10pt、短句 17pt），本轮修掉。
3. **流程问题记在案**：R6 之后连续几轮是按「发现 bug → 修 → 报」推进的，没有开会、没有方案表。
   本轮恢复：议题 → 五组发言 → 取舍 → 方案（可测量验收）→ 实施 → 复核。
4. **下一轮起，每轮必须有一个「用户能感觉到」的板块**，不能整轮只做内部指标。

## 各组发言

### 一 · 应用设计

**1. 颜文字大小不一（已修）。**
- 证据：`EmojiPanelView.Cell` 固定 17pt 且 `adjustsFontSizeToFitWidth`，长颜文字被压到 10pt、短的保持 17pt；
  真机上就是「有的偏大有的偏小」。
- 改法：颜文字格子按字数反推字号（`side × 1.5 / 字数`，夹在 10–19），emoji 格子仍按格子 78%。
- 验收：同屏颜文字视觉高度差 ≤ 15%（CI 快照 `day_mosto_kaomoji.png` 目测 + 格子字号一致性）。

**2. 表情面板还差两处。**
- 证据：改后快照里最后一行仍贴近「拼音」条；分组标题占掉近半行。
- 改法：底部留白 12 → 18（已改）、标题 26 → 20（已改）；下一轮再看是否还要收紧行距。
- 验收：快照里最后一行完整可见、不压字。

### 二 · 内容展示

**1. 对外数字必须带口径。**
- 证据：本轮汇报里同时出现 `92.13`（305 句、`-O`、带句子模型）与 `72.50`（混输 80 句）；不加口径读者会混。
- 改法：以后每个数字后缀「集合 / 配置 / 采样次数」。
- 验收：`rounds/` 与 `docs/` 里新写的段落，凡百分比均带这三项。

**2. 把「退步」写出来。**
- 证据：漏按功能把 `mixed.sentences.top1` 从 73.75 拉到 72.50，仍在门槛上但不该被忽略。
- 改法：已在 R6 与 `docs/DIAGNOSIS.md` 各记一处；本轮不撤。

### 三 · 应用交互

**1. 「灵活」的三种来源，我们只补了第一种。**
- 证据（事实）：同音字排序（已补两条规则）；beam 16/40、模型权重、上下文长度都无收益（`docs/DIAGNOSIS.md` 三张表）。
- 推断：剩下两种是**联想**与**个人习惯的收敛速度**——普通输入法在这两项上积累多年。
- 改法：下一轮起用一个可测的板块做「联想」：同一前文后，首屏候选里出现正确下一个词的比例。
- 验收：构造 30 条「上句→下句」用例，命中率有基线、有改动后的数字。

**2. 的/得 规则层已上线，但只覆盖「的＋补语」。**
- 证据：`标题写的太长了`、`最近睡的不太好` 两条修好；`他会自己穿鞋了`（他/她）未动。
- 改法：他/她 不做硬规则，交给上下文偏好学习（已上线）。
- 验收：偏好学习「改一次后是否稳定」需要真机验证，本轮标**未验证**。

### 四 · 品牌 IP 运营

**1. Mosto 在两处出现，尺寸必须自成一套。**
- 证据：底栏 26pt、颜文字分区标题 22pt（本轮随标题 26→20 调整）。
- 改法：定一条规矩——**Mosto 的脸在底栏与标题里高度一致，且不小于相邻图标的 90%**。
- 验收：快照里目测 + 代码里的两个常量写死（26 / 22 是同一族的两个尺寸，记录在此）。

### 五 · iOS 应用开发

**1. 延迟验收必须多采样。**
- 证据：同一二进制 `fuzz.p99` 在 8.2–9.9 ms 之间跳动；2–3 次采样判不了 3% 的提速。
- 改法：新增 `build/latency.sh`，同一二进制跑 N 次取中位数与极值；本轮基线：**中位 8.90 ms**（3 次采样）。
- 验收：以后每项提速都用它，结论里写「采样 N 次，中位 X」。

**2. R6 剩下的两项提速（`Path.edges` 父指针、`query/encode` 缓冲复用）本轮不做。**
- 理由：本轮预算给了用户能感觉到的两块（颜文字、的/得）；提速留在下一轮，且必须先有 `dump` 逐字相同 + 多采样。

## 冲突与取舍

- **「继续修同音字」vs「做联想」**：同音字还剩 22 条（他/她 3、其它 19），继续做收益递减且需要语料；
  联想是用户能直接感觉到的「灵活」。裁决：**下一轮做联想测量**，同音字只保留偏好学习的自然收敛。
- **「先做提速」vs「先做观感」**：产品负责人真机反馈的是观感与手感，提速是内部指标。裁决：**观感优先**。
